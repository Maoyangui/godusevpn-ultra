## 执行顺序与门槛

1. **处理本批实现缺陷**：按 A01–A21、C01–C06 和 U01–U07 台账区分确认缺陷、已修待验、保留限制与后续新增需求。当前实现的诊断、维护互斥、恢复记录、助手重连、失效检测与同快照导出缺陷必须处理；源码已修但必需实测未过的继续待验收。A12/N06 等路线图不要求在首 beta 全部开发完成，不以把所有编号改成“关闭”作为发版条件。
2. **逐功能回对原计划**：R01–R14及N/S/B/D每项记录实现/条件/引导/未实现、证据、实际限制。条件引导不能当作实现；不能靠改README把缺失工作关闭。功能范围出现实质调整先明确记录原因。
3. **受控 Windows 实测**：在可恢复的测试环境中，先核对新包只读/身份/恢复，再分批验证安装、浏览器和网络；每项记录目标版本、预期、读回、冲突或失败及恢复证据。只读报告或旧包单项通过不能替代这些行为验证。可能失联的测试必须先证明恢复路径，不新增宽泛放行伪造通过。
4. **发布前全量审计**：独立检查源码、UI、默认值、权限、外联、备份、卸载、原隧道独立与敏感数据；必要的测试、vet、界面与原目录完整性检查通过，修复后重核相关范围。
5. **公开仓库与说明**：创建新仓库；英文默认README及中文说明写实际实现、安装、恢复、测试证据和限制。保留原来源与许可。审阅后提交并推送，不携带本地测试账号或凭据。
6. **构建与预发行**：上述本批范围的发布门槛通过后，使用独立 Windows 工作流，默认 live 开关关闭；核对 tag/应用资源、GUI/CLI/服务和扩展、校验清单及源码对应关系。GitHub 标记 Prerelease，不标为稳定版或所有隐私保护已完成。CI 通过本身不替代必需实机验收。
7. **构建后全量审计**：核对远端commit/tag、CI结论、下载包哈希、PE架构/资源/权限、内嵌前端、安装清单、README承诺和实际功能。发现问题先修复并重新构建受影响产物，不用旧包测试证明新包。
