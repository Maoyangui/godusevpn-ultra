## 真实订阅与隧道

在 VM 内通过 CLI 设置前面对话提供的测试订阅并刷新：`profile` 退出码 0，`refresh` 退出码 0，节点列表退出码 0，共读回 19 行节点。随后执行 `connect`，退出码 0；15 秒后状态回读为 `connected`、`TUN=true`、`strict=true`、`IPv6=false`，没有直连回退。

通过 Azure Run Command 的 SYSTEM 会话直接请求 `https://api.ipify.org?format=json`，返回 JSON IP；`https://ipwho.is/` 同样返回成功，归属地字段可读。该出口请求是在 Ultra 已连接的 VM 上完成，未改动本机网络设置。

`127.0.0.1:9800` 在 SYSTEM Run Command 会话中没有监听者，因此用该端口测试得到连接失败；这只说明该本地代理端口不向 SYSTEM 会话暴露，不能推断用户桌面会话的浏览器代理失败。为避免误判，已使用 TUN 直出请求完成出口验证。

最后执行 `disconnect`，退出码 0；8 秒后状态回读为 `disconnected`，配置仍保持 `TUN=true`、`strict=true`。本轮没有留下连接状态或本机网络变更。

## 隐私与浏览器宿主

- `godusevpn-cli privacy report` 在 VM 上实际运行并返回结构化 JSON；报告保留 `unknown`、`limited`、`planned` 等边界状态，没有把观察结果写成全局保护。
- 浏览器宿主进程确实被启动尝试；没有通过 Ultra 严格连接和父进程认证管道时返回固定 `{"type":"error","code":"start_refused"}`。这证明拒绝门禁生效；普通 Windows 构建现在已进入同一严格 native Start 链路，但本次 SYSTEM Run Command 没有普通用户父进程，仍不能把该次结果写成窗口/多版本浏览器通过。
- WebView2 运行时和宿主文件存在不等于 Chrome/Firefox 多版本、WebGPU、WebRTC、代理浏览器出口或 OOPIF 已实测。普通发行构建现在开放同一严格 native Start 链路，但本次 SYSTEM 会话没有普通用户父进程，不能把本次结果写成真实窗口或导航通过。
