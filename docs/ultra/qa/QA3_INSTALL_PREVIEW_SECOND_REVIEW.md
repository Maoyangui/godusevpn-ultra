## Runtime compatibility follow-up: v1 is not ready to reuse

After this pure/static review, the root operator reported a real-machine v1 preview attempt: `effectiveSystemCaller=true`, preflight failed with `SCM_unknown`, `whatIfStarted=false`, no product/installation requested. This is a fail-closed native compatibility failure, not a successful preflight. Freeze v1 unchanged; do not reuse its SCM helper in actual installation or treat unknown as absent.

A separate **pure managed Windows PowerShell 5.1 binder experiment**, with no native/SCM calls, showed that invoking an emitted static method with a `[string]` parameter directly as `$type::Classify($null)` delivers an empty string. Invoking the same method through `MethodInfo.Invoke(..., [object[]]@($null))` delivers a true null. V1 declares both optional OpenSCManagerW pointer parameters as strings and calls them directly with PowerShell `$null`. This supplies an empty database name rather than the documented null/default database. The official API explicitly accepts an empty machine name but specifies null or SERVICES_ACTIVE_DATABASE for the database name: [OpenSCManagerW](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-openscmanagerw).

The binder behavior is confirmed by the pure experiment; attributing the exact remote native failure/error code still needs the root operator's independent evidence. `Vps-Qa3InstallV2.ps1` and `Vps-Qa3ScmReadbackV2.ps1` now use true null pointers (`IntPtr.Zero`) and preserve strict absence/error handling; their local checks passed (79 install-preview checks plus 11 fictional scenarios, and 22 SCM-readback AST checks). Last-error capture across PowerShell boundaries is also a reason to keep unknown as unknown. No real service/token/native operation has been run with v2; a real-machine readback is still required.
